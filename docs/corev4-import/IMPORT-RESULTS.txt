RANKING AND CONTEXT PRESERVATION
Existing unigram weights are unchanged. A new form receives weight 1, an explicit
conservative prior, not an observed usage frequency. Existing frequencies win on
overlap. This admits words without assigning arbitrary large weights that could
make rare terms override common corrections. Prior 1 is not optimized frequency
calibration; rare new terms may rank low in fuzzy suggestions and completions.

The builder first reconstructs the previous 61,082-word model and its contexts.
Only then does it union the CoreV4 forms, sort by descending frequency and lexical
tie break, and remap all old numeric IDs into the new ordering. Building contexts
after vocabulary expansion would have changed formerly OOV corpus boundaries;
that is deliberately avoided. Both context totals and ordered continuations are
preserved exactly by surface form, as are sentence starters:
  29,206 bigram contexts / 241,198 continuations
  218,403 trigram contexts / 386,447 continuations
  20 sentence starters
New forms generally lack dedicated n-gram evidence; existing backoff and personal
learning apply. The unigram normalization sum gains 53,201 units even though old
word weights are fixed. There is no claim of bit-identical final decoder scores.
The trie grows from 146,823 to 275,561 nodes.

WHY KBLM V6
V5 permits 65,534 vocabulary forms, below the requested full union. V6 uses
32-bit word IDs and retains sorted context arrays with binary search. The C++
reader and Swift comparison reader are updated together. Older v2-v5 packs stay
readable; the v5 builder path remains available for reproducibility.
All integers are little-endian; records are packed without native alignment:
  header: nine u32 values, 36 bytes; magic, version=6, word count, bigram context
    count, bigram entry count, trigram context count, trigram entry count, trie
    node count, starter count
  frequencies: u32 per word
  offsets: u32 per word plus one final offset
  bigram context: u32 contextID,total,start,count (16 bytes), sorted by contextID
  bigram continuation: u32 wordID,count (8 bytes)
  trigram context: u32 firstID,secondID,total,start,count (20 bytes), sorted by pair
  trigram continuation: u32 wordID,count (8 bytes)
  trie: u8 label,u8 childCount,u32 firstChild,u32 wordID,u32 maxFrequency (14 bytes)
  starter: u32 wordID,count (8 bytes)
  blob: concatenated UTF-8 spellings; offsets delimit each spelling
Trigram comparison uses (uint64(firstID)<<32)|secondID, not v5's 16-bit packing.
Nonterminal trie IDs are 0xffffffff. Runtime bridge IDs remain signed Int32;
the builder limits word count accordingly. Ranges/counts and IDs are checked by
the production native reader. High-ID tests cover context collisions, starters,
trie terminals, malformed contexts and truncated records under ASan/UBSan.

LIMITS
This is full stored-form admission with the four documented exceptions, including
accented, hyphenated and other spellings outside the old ASCII admission filter.
Exact UTF-8 membership is available; admission does not implement accent-insensitive
matching, Unicode normalization, new keyboard keys, punctuation tokenization or
new spatial costs for accented letters. The source union includes 106 non-ASCII
forms, 846 forms containing hyphens and 718 containing digits (categories overlap),
including some URL-like stored forms. Full admission retains these rather than
claiming that every entry is a curated everyday English word. CoreV4 display/capitalization flags are
preserved in raw assets but not applied by iOS. A CoreV4 stored spelling is not a
promise that it is suitable as an automatic correction in every situation.

Larger vocabulary and wider records increase mapped storage and search work.
The pack is memory mapped, but touched pages and runtime indices consume RAM.
No inference that it is faster or uses less RAM follows from having more words.
Physical iPhone latency, memory pressure and keyboard jetsam remain device tests.
An unsigned cross-compiled device bundle measures storage, not phone runtime.
